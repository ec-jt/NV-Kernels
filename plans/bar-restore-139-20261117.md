# Controlled reset and BAR restoration on server .139

Status: published as experimental pre-release hotplug-barfix1-7.0.0.
Controlled reset and CUDA checks passed on .139, but a spontaneous fatal
fault recurred afterward. Not qualified for fleet deployment or automatic
fatal-error recovery. Workloads held during further link testing.

Host: 10.101.8.139, UUID e9184000-7983-11ec-8000-18c04db010d2.
Base source: a75690917801d5a6250517933c3d647ff01ac202.
Candidate: 7.0.0-hotplug-barfix1. Persistent fallback: 7.0.0-hotplug.
AER and DPC remain enabled throughout. No switch firmware/configuration writes.

## Reproduced failures on the existing hotplug kernel

The original pair at 0000:04:00.0 and 0000:05:00.0 was unavailable. GPU
workloads and their launch services were held. NVIDIA DRM removal blocked;
a controlled maintenance reboot stalled and required one BMC reset. The
maintenance boot returned all eight GPUs with their actual 32 GiB BAR1
apertures and complete forwarding windows.

A controlled reset_subordinate write on 0000:03:00.0 produced a real reset,
but returned ENOTTY. pciehp treated the intentional transition as removal
and re-added GPU 04. The kernel logged both an out-of-bounds VF BAR index 7
in sriov_restore_vf_rebar_state() and a shift-by-64 error. Config reads during
reset were not checked before indexing the six-element VF BAR-size array.
All eight GPU hardware BARs passed a read-only check after re-enumeration.

The original test used buffered Python sysfs output. Subsequent tests use a
single os.write() so error handling cannot retry a buffered write on close.
The ENOTTY result must not be interpreted as evidence that no reset occurred.

At 01:24:58 UTC, with NVIDIA still unloaded and GPU jobs stopped, switch port
0000:03:01.0 reported RxErr, followed by ERR_FATAL and root DPC containment.
Recovery failed because endpoints and the Switchtec management driver lacked
error_detected callbacks. Switch upstream port 0000:02:00.0 then had zero bus
numbers, disabled forwarding windows and Mem-/BusMaster-. Its physical
upstream link remained Gen4 x16. Consequently the two downstream ports and
GPUs were inaccessible, independently of NVIDIA's driver enumeration.
This establishes a failed recovery sequence, not the cause of the initial
receiver error. It also shows that loss of both GPUs need not mean both
physical links independently failed.

## Candidate changes

- Reject failed/all-ones ReBAR configuration reads in PF and VF restoration.
- Bound-check BAR counts and indices; avoid converting empty resource sizes.
- Mark intentional bus-reset link changes across the affected subtree until
  save/reset/restore completes, using the existing PCI hotplug coordination
  API. A genuine link still down after the operation remains actionable.

These changes do not add NVIDIA AER callbacks, claim successful recovery of
an unresponsive GPU, or restore CUDA contexts. The separate DPC failure path
can still skip bridge slot_reset callbacks when a device cannot recover.

## Separate storage finding

NVMe ports 45/46/47 report receiver/data-link errors. Root 40:03.1 also
logged fatal containment during boot. This delayed candidate startup but
SSH and the root filesystem returned; root remained mounted read/write.
The previous hotplug boot had the same class of NVMe AER errors.
NVMe 45:00.0 was observed at 16 GT/s x4 with a 16 GT/s target.

Follow-up comparison with 10.100.8.107 found that lab_nvme_gen3=1 is consumed
by an initramfs script, not a kernel parser; the kernel's unknown-parameter
message alone does not establish failure. The script on .139 explicitly
allowed only 7.0.0-hotplug and consequently skipped the -barfix1 candidate.
.107 runs 7.3.0-hotplug-nova-v46, whose packaged initramfs copy explicitly
allows that version. Its boot log confirms the helper ran and found its two
NVMe links already at or below Gen3; their current widths are x4 and x2.
The source copy in .107's /etc still has the old version gate, so rebuilding
that host's initramfs without correcting the source would lose the adjustment.
No changes were made to .107.

At the user's request, scripts/lab-nvme-gen3-initramfs removes the version
gate entirely. The helper defaults to disabled; only lab_nvme_gen3=1 enables
it, and the last explicit occurrence wins. Absent, zero or invalid values do
nothing. The platform, dedicated-parent and unbound-storage checks remain.
The actual shell helper passed fixture tests for no-op/default behavior,
explicit activation, duplicate-argument precedence, Gen3 target/retrain and
skipping bound controllers. Its .139 source was backed up and the candidate
initramfs regenerated. Recovery-boot verification passed. No live storage
retraining was performed. The separate NVMe errors on the old kernel also
require investigation; they are not explained solely by the candidate's
version-gate mismatch.

The helper must be included in the selected kernel's initramfs. Install it
as /etc/initramfs-tools/scripts/init-top/00-lab-nvme-gen3 and regenerate that
kernel's initramfs. No kernel-release string is checked. lab_nvme_gen3=1
opts in; lab_nvme_gen3=0, an absent flag, or an invalid value does nothing.
The G292 platform check remains intentionally in place.

## Native downstream DPC experiment

The port driver enables DPC on a downstream port only if that port has an
AER service or pcie_ports=dpc-native is set. The AER service is normally
provided on Root Ports/RCECs. Thus pcie_ports=native alone left the
Switchtec downstream DPC controls at Trigger:0, with no DPC service bound,
even though root DPC was active. This was verified in sysfs and config
space before changing the boot entry.

A one-time entry added pcie_ports=dpc-native alongside pcie_ports=native.
The graceful reboot succeeded. Boot d8b16ea4-3c1a-45dc-baf9-e7da8aeaf09b
uses the same released candidate image, with AER and DPC active on all
eight GPU downstream ports. The persistent fallback was unchanged.

At 02:56:14 and 02:56:20, before NVIDIA loaded, 03:01.0 again reported
RxErr and lost its link. Switchtec stack 4 recorded receiver/surprise-down
errors and two downstream DPC events. This time Linux removed/re-added
only 05:00.0/05:00.1. Its 32 GiB BAR and ancestor windows were restored,
04:00.0 remained accessible, and switch management remained available.
There was no simultaneous loss of the entire first switch branch.

The absence of a detailed DPC journal message for those events is explained
by dpc_handler(): for a hotplug bridge with Surprise Down set, it takes
dpc_handle_surprise_removal(), clears status, and allows hotplug to handle
removal rather than invoking the normal fatal-error callback sequence.
Switch counters and the PCI flight recorder are therefore retained as
additional evidence. This is driver-detached re-enumeration, not evidence
that running CUDA contexts survive a failure.

## Single-link Gen3 trial

At 03:00:41 UTC, with NVIDIA unloaded and both GPU05 functions unbound,
only port 03:01.0 was capped from Gen4 to Gen3 and retrained once.
Original Link Control 2 value 0x0004 was saved. Gen3 x16 established,
neighbour port 03:00.0 remained Gen4 x16, and all eight GPUs passed the
actual BAR/window audit. No AER mask or switch firmware setting changed.

NVIDIA/UVM were loaded explicitly, with the prior 400 W power limits and
persistence restored. All eight GPUs passed the initial ten-second CUDA
pattern test. A bounded trial then alternates twenty-second checks on
GPU05, verified 64 MiB P2P copies in both directions with GPU04, and
twenty-second idle periods. It stops on errors and never resets devices.
Results are recorded in downstream-dpc-gen3-trial/trial.json.

The Gen3 trial passed all fifteen cycles in 677.94 seconds, with no new
Switchtec error counts, link removals or Xids. Idle transitions to Gen1/P8
still occurred normally; clocks were not locked. This is a CUDA memory and
copy correctness/load-idle trial, not a maximum-power burn-in.

For an A/B comparison, the idle NVIDIA modules were unloaded and only
03:01.0 was returned to Gen4 at 03:15:07 UTC. BAR audits passed before the
driver was reloaded with the same 400 W limits and persistence settings.
The same initial eight-GPU CUDA check passed. During the first subsequent
GPU05 check, RxErr appeared at 03:15:58.946 UTC, followed by Xid 79 on
05:00.0 at 03:15:59.749. CUDA failed approximately twenty seconds into
the comparison run. Stack 4 gained 35 receiver errors, one Surprise Down
and one DPC event; the neighbour and switch management remained accessible.
NVIDIA also marked the other GPUs as requiring OS reboot (Xid 154), so
surviving PCI access must not be equated with healthy existing CUDA contexts.

The recorder preserved a completed 512-entry stack-4 hardware trace. Its
trigger entry has UAER set, with no RST or BAD_ECRC flags in that capture.
Packet-level interpretation remains to be validated; this does not identify
a specific defective component or prove that switch firmware reset the GPU.
A second safe-mode NVIDIA bug report was saved before recovery.

Returning the link to Gen3 and unloading the driver did not alone restore
GPU05: its hardware BAR bases and ReBAR size disagreed with Linux's cached
resources. A preliminary driver reload consequently enumerated only seven
GPUs. With drivers unloaded again, only the unbound 05:00.1 and 05:00.0
functions were removed, followed by a rescan of their dedicated parent
03:01.0. All eight actual BAR/window audits then passed and the driver
initialized all eight GPUs without a chassis reboot or switch reset.
All eight then passed fresh CUDA memory checks (thirty seconds on GPU05,
ten seconds on the others), and the affected pair again passed verified
64 MiB peer copies in both directions. The completed hardware trace was
preserved before re-arming stack 4 for the next fault.
This is a drained, explicit recovery procedure, not automatic recovery of
running jobs. Never use an ordinary reset to save/restore already-corrupt
hardware BAR values as if they were a known-good configuration.

The GPU05 cap is a temporary live setting; it is not installed fleet-wide
or made a boot default. It reduces maximum link bandwidth and does not
prevent normal idle Gen1/P8 transitions. A clean short trial alone cannot
prove a permanent hardware fix or isolate the physical component at fault.
The A/B result strongly implicates Gen4 link operation on this path. It
does not distinguish signal integrity, equalization, switch/card firmware,
connector/riser or board-level causes. Gen3 is an interim mitigation.

## Operational state

The candidate is installed separately and running. The persistent GRUB
saved_entry remains fleet-hotplug-gen3, pointing to 7.0.0-hotplug. Candidate
boot now uses the one-time barfix-dpc-139-20261117 entry. No fleet rollout
has been performed. A read-only PCI configuration recorder remains active
as barfix139-recorder.service; it records link changes and heartbeats.
barfix139-switch-recorder.service additionally captures switch error
counters/events every five seconds and retains LTSSM history on changes.
It never clears counters or resets hardware. Log rotation and a four-fault
snapshot limit per boot bound storage use.
Switchtec hardware trace buffers on stacks 1/3/4 were also armed using the
verified ChipLink event layout. Diagnostic Unsupported Requests are excluded
from the analyzer trigger only; PCIe/AER masks are unchanged. Completed
hardware traces are saved rather than silently overwritten.

Temporary module-loading restrictions are removed after validation and the
candidate initramfs regenerated. The maintenance state records restoration
of the original service and container restart policies. All five previously
running containers were started successfully, along with their original
active monitoring/scheduler services. After the recurrence, all five were
stopped cleanly and the maintenance holds were re-established. The recovery
boot and short CUDA checks now pass, but workload holds, driver-autoload
guards and the PCI recorder remain in place pending investigation of the
spontaneous failure. NVIDIA and UVM were explicitly loaded for these checks.
The downstream DPC and single-link speed trials above are separate from
the released BAR-restoration changes. The .107 host and the rest of the
fleet were not modified.
